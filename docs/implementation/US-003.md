# US-003 — Proteção de rotas autenticadas

## O que foi pedido

Garantir que rotas de Drone, Mapa e Missão só sejam acessíveis com um token de
acesso válido; requisições sem token, com token inválido/expirado, são
recusadas com erro de não autenticado; com token válido, o usuário autenticado
é identificado e a lógica de negócio prossegue restrita aos recursos desse
usuário (RF-001.5, RN11).

## Passo a passo do que foi implementado

- `src/common/middlewares/autenticacao.middleware.ts` — `autenticacaoMiddleware`:
  lê o header `Authorization`, exige o formato `Bearer <token>`, valida o
  token com `verificarToken` (de `common/security/token.ts`, US-002) e anexa
  `req.usuarioId = payload.sub`. Qualquer falha (header ausente, formato
  errado, token inválido/expirado/assinado com outro segredo) chama
  `next(new UnauthorizedError())` — nunca responde diretamente, delegando ao
  middleware de erro global (`tratamento-erros.middleware.ts`), conforme
  convenção de `stack.md`.
- Extensão de tipo `Express.Request` (`declare global` no próprio arquivo do
  middleware) adicionando o campo opcional `usuarioId?: string`, para que
  controllers de módulos futuros (Drone, Mapa, Missão) leiam
  `req.usuarioId` com tipagem, sem `any`.

## Alternativas de implementação consideradas

- **Consultar o banco para confirmar que o usuário do token ainda existe** —
  descartada nesta história. O middleware só valida a assinatura/expiração do
  JWT (stateless, ADR-002) e não faz round-trip ao banco a cada requisição.
  Se um usuário fosse excluído após emitir um token (cenário hoje impossível,
  já que não há endpoint de exclusão de usuário no backlog), o token
  continuaria "válido" no sentido de assinatura, mas qualquer operação sobre
  Drone/Mapa/Missão não encontraria recursos pertencentes a esse `usuarioId`
  — o efeito prático de RN11 já é coberto pela checagem de ownership em cada
  módulo de recurso, sem precisar de uma consulta extra aqui.
- **Middleware aplicado globalmente em `app.ts` (`app.use(autenticacaoMiddleware)`
  antes de todas as rotas)** — descartada porque `/usuarios` (cadastro) e
  `/auth/login` (login) precisam continuar públicos (fora de escopo desta
  história, conforme a própria US-003). O middleware é aplicado por rota (ou
  por router), não globalmente; os módulos de Drone/Mapa/Missão (sprints
  seguintes) vão registrá-lo explicitamente em seus routers.
- **Rota de teste dedicada (`/_teste/protegida`) montada só no arquivo de
  teste, não em `app.ts`** — não é gambiarra de produção: nenhuma rota real
  usa o middleware ainda nesta sprint (Drone é a primeira, na Sprint 02), e
  testar o middleware isoladamente evita acoplar seu teste à existência de um
  módulo de recurso que ainda não existe.

## Como foi testado

Plano de testes: `docs/tests/US-003-plano.md` (11 casos). Todos os 11
cobertos em `src/common/middlewares/autenticacao.middleware.spec.ts`:

- Casos 1–9 via Supertest, contra uma app de teste local que monta
  `/usuarios`, `/auth`, a rota protegida de teste e o middleware de erro
  global — exercitando o fluxo real de cadastro → login → acesso.
- Casos 10–11 via chamada direta ao middleware com `req`/`res`/`next`
  mockados, confirmando o contrato (`next(erro)` vs. `next()` sem argumento).
- Caso 2 do plano de US-002 (token utilizável em rota protegida) fechado pelo
  caso 1 desta história.

Suíte rodada com `pnpm test -- autenticacao`: 11 testes, todos passando.

## Próximos passos / dívidas técnicas conscientes

- A checagem de ownership por recurso (RN11 — "não encontrado" quando o
  recurso pertence a outro usuário) não é implementada aqui; é responsabilidade
  de cada módulo de recurso, a partir da Sprint 02 (Drone).
- Nenhuma dívida técnica consciente deixada nesta história.
