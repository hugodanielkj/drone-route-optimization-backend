# US-012 — Alterar ponto de carregamento do mapa

## O que foi pedido

Usuário autenticado altera o ponto de carregamento de um mapa seu; mapa de
outro usuário retorna não encontrado; alteração bem-sucedida desativa toda
Missão ativa associada ao mapa (RN13).

## Decisões de contrato tomadas com o usuário

- **Rota**: sub-recurso aninhado `PATCH /mapas/:id/ponto-carregamento`, em vez
  de um `PATCH /mapas/:id` genérico com campos opcionais mutuamente
  exclusivos — mantém uma responsabilidade por rota e um schema por operação,
  consistente com RNF-003.3 (nenhuma rota trata Coordenada isoladamente fora
  do escopo de um Mapa).
- **RN17 aplicada contra estado persistido, não contra o payload**: a nova
  coordenada é comparada contra os pontos de irrigação já salvos no banco
  daquele mapa (carregados via `mapaService.buscarPorId`), não apenas contra o
  próprio payload da requisição — diferente de US-009, onde a checagem era
  100% sobre o corpo da requisição.
- **`ConflictError` (409), não `ValidationError` (400) manual**, para RN17
  neste contexto — decisão explícita do usuário. Motivo: `ValidationError`
  nunca é construída manualmente no projeto (só nasce de `ZodError`, que só
  enxerga o payload); toda regra que depende de consultar o banco já usa
  `ConflictError` (RN15 em `drone.excluir`, nome duplicado em
  `usuario.cadastrar`). RN17 em contexto de update é estruturalmente a mesma
  categoria.

## Passo a passo do que foi implementado

- `src/modules/mapa/mapa.schema.ts` — `alterarPontoCarregamentoSchema`:
  reaproveita `coordenadaSchema` (já existente, validação `.finite()`) sem
  alteração — só `{x, y}`.
- `src/modules/mapa/mapa.service.ts` — `mapaService.alterarPontoCarregamento(usuarioId, mapaId, input)`:
  1. `buscarPorId` (ownership, já traz `pontosIrrigacao` via `include`).
  2. Compara `input` contra cada ponto de `mapa.pontosIrrigacao`; lança
     `ConflictError` se colidir (RN17).
  3. `prisma.$transaction([mapa.update, missao.updateMany])` — mesma forma
     array já usada em `droneService.editar`: atualiza o ponto de
     carregamento e desativa Missões `ATIVA` do mapa (RN13) atomicamente.
- `src/modules/mapa/mapa.controller.ts` — `alterarPontoCarregamento`: parseia
  o body, chama o service, formata via `formatarMapa`, responde `200`.
- `src/modules/mapa/mapa.routes.ts` — `PATCH /:id/ponto-carregamento`
  registrado.

## Alternativas de implementação consideradas

- **`PATCH /mapas/:id` genérico** — descartada (ver decisão de contrato
  acima).
- **Reaproveitar a chave string `chaveCoordenada` do schema para a comparação
  RN17** — descartada: essa função é interna a `mapa.schema.ts`, usada para
  comparar coordenadas dentro do mesmo array de payload. Aqui a comparação é
  ponto-a-ponto contra linhas do Prisma já carregadas; `===` direto em `x`/`y`
  é mais simples e não exige exportar um utilitário do schema para o service.

## Como foi testado

Plano de testes: `docs/tests/US-012-plano.md` (11 casos). Todos cobertos em:

- `src/modules/mapa/mapa.controller.spec.ts` (e2e): alteração bem-sucedida,
  alteração para a mesma coordenada, tipo inválido, payload incompleto, mapa
  inexistente, mapa de outro usuário (com verificação de não alteração),
  ausência de token, colisão com ponto de irrigação existente (RN17, 409), e
  os 3 casos de RN13 (desativação em cascata de múltiplas Missões `ATIVA`,
  idempotência sobre Missão `DESATIVADA`, isolamento entre mapas).
- `src/modules/mapa/mapa.service.spec.ts` (unitário): atualização bem
  sucedida, `NotFoundError` para mapa de outro usuário, `ConflictError` para
  RN17, desativação de Missão ativa associada.

Suíte rodada com `pnpm test`: 9 suítes, 191 testes (à medida que as demais
histórias da sprint foram implementadas), todos passando. `pnpm typecheck`
sem erros.
