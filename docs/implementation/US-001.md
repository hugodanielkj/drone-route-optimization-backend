# US-001 — Cadastro de usuário

## O que foi pedido

Permitir que um visitante se cadastre informando `nome` e `senha`, rejeitando
nomes já cadastrados, persistindo a senha exclusivamente como hash, e validando
o payload via DTO antes de qualquer lógica de negócio (RF-001.1 a RF-001.3,
RN09).

## Passo a passo do que foi implementado

- `prisma/schema.prisma` — model `User` (`id`, `nome` único, `senhaHash`,
  `createdAt`), como parte do schema completo definido já na Sprint 01 (ver
  `docs/sprints/sprint-01.md`).
- `src/common/security/senha.ts` — `hashSenha`/`compararSenha` centralizados
  (bcrypt via `bcryptjs`, ver ADR-001), reutilizáveis pelo módulo de login
  (US-002) sem duplicar a lógica de hashing.
- `src/common/errors/app-error.ts` — hierarquia de erros de aplicação
  (`ValidationError`, `ConflictError`, `UnauthorizedError`, `NotFoundError`),
  cada uma com seu `statusCode`, para o middleware de erro global traduzir em
  resposta HTTP.
- `src/common/middlewares/tratamento-erros.middleware.ts` — middleware de erro
  global (único lugar que decide status/corpo da resposta de erro), tratando
  `ZodError` (400 com detalhes de validação) e `AppError` (status próprio de
  cada subclasse).
- `src/modules/usuario/usuario.schema.ts` — schema Zod (`nome` string não vazia,
  `senha` mínimo de 8 caracteres). Campos extras no payload são ignorados por
  padrão pelo Zod (não usei `.strict()`), conforme decisão registrada no plano
  de testes (caso 11).
- `src/modules/usuario/usuario.service.ts` — `cadastrar()` faz hash da senha e
  tenta `prisma.user.create()` diretamente; captura o erro `P2002` (violação da
  constraint `@unique` em `nome`) e o traduz para `ConflictError`. A checagem de
  duplicidade não é feita com um `findUnique` prévio — ver alternativas
  descartadas abaixo.
- `src/modules/usuario/usuario.controller.ts` / `usuario.routes.ts` — parse do
  DTO, chamada ao service, `try/catch` explícito chamando `next(erro)` (padrão
  definido em `stack.md`, já que Express não captura rejeições de Promise
  automaticamente).
- `src/app.ts` / `src/server.ts` — montagem da aplicação Express, registro do
  router `/usuarios` e do middleware de erro global por último.

## Alternativas de implementação consideradas

- **Checar duplicidade de nome com `findUnique` antes de `create`** —
  descartada porque não é segura sob concorrência (duas requisições podem
  passar pela checagem antes de qualquer uma criar o registro — condição de
  corrida). Optei por confiar na constraint `@unique` do banco como fonte
  única de verdade e capturar o erro de violação, que é atômico. Coberto pelo
  caso 6 do plano de testes (`usuario.service.spec.ts`, teste de concorrência
  com `Promise.allSettled`).
- **Normalizar o `nome` (lowercase) antes de persistir** — descartada porque
  RF-001 não define essa regra explicitamente, e normalizar silenciosamente
  mudaria o comportamento percebido pelo usuário (dois nomes visualmente
  diferentes colidindo). Documentado como decisão explícita no plano de testes
  (caso 2): unicidade é sensível a caixa.
- **Retornar a senha ou o hash no corpo da resposta de cadastro** — descartada
  por princípio de segurança (nunca expor o hash, mesmo que irreversível);
  o `select` do Prisma já restringe os campos retornados a `id`, `nome`,
  `createdAt`.

## Como foi testado

Plano de testes: `docs/tests/US-001-plano.md` (12 casos). Todos os 12 casos
foram cobertos:

- `src/modules/usuario/usuario.service.spec.ts` — casos 12 (hash bcrypt válido,
  nunca texto plano), 7 (nome duplicado rejeitado no nível de service) e 6
  (concorrência: exatamente um cadastro vence).
- `src/modules/usuario/usuario.controller.spec.ts` — casos 1, 2, 3, 4, 5, 7
  (repetido no nível HTTP, verificando status 409), 8, 9, 10 e 11, via
  Supertest contra a aplicação Express real (`createApp()`), com banco de
  dados de teste real (`backend_ic_test`), limpo antes de cada teste
  (`src/test/setup.ts`).

Suíte rodada com `pnpm test -- usuario`: 13 testes, todos passando.
