# US-020 — Consultar detalhe de uma missão

## O que foi pedido

`GET /missoes/:id` retorna o detalhe completo de uma missão do usuário
autenticado (todas as pernas de rota, consumo energético total e status);
id inexistente ou de outro usuário retorna não encontrado.

## Decisões de contrato tomadas com o usuário

Nenhuma decisão de contrato nova específica desta história — reaproveita as
já tomadas em US-016 (`formatarMissao` completo, com `pernas`) e a
distinção listagem-vs-detalhe já confirmada em US-019.

## Passo a passo do que foi implementado

- `src/modules/missao/missao.service.ts` — `buscarPorId(usuarioId,
  missaoId)`: como `Missao` não tem `userId` próprio, a checagem de
  ownership é feita num único `prisma.missao.findFirst({ where: { id:
  missaoId, drone: { userId: usuarioId } } })`, em vez do padrão de duas
  etapas (`findUnique` + comparar `userId`) usado em `drone`/`mapa` —
  `!missao` cobre tanto "não existe" quanto "existe mas é de outro usuário",
  lançando `NotFoundError` em ambos os casos (nunca revela a existência do
  recurso a quem não é dono, mesmo padrão das demais entidades).
- `src/modules/missao/missao.controller.ts` — handler `buscarPorId`,
  respondendo `200` com `formatarMissao` (já existente, com `pernas`
  completo).
- `src/modules/missao/missao.routes.ts` — `GET /:id` registrado.

## Alternativas de implementação consideradas

- **Reaproveitar o padrão de duas etapas de `drone`/`mapa`** — descartada:
  exigiria uma consulta adicional para obter o `userId` do drone/mapa
  associado antes de comparar; o filtro relacional do Prisma resolve
  existência e ownership numa única query.
- **Permitir consulta pelo par (drone, mapa), não só por id** (mencionado
  como alternativa em RF-004.13) — descartada nesta história: os critérios
  de aceite de US-020 só pedem consulta por id; consulta por par ficaria
  redundante com o próprio `POST /missoes` (que já retorna o estado atual da
  Missão do par).

## Como foi testado

Plano de testes: `docs/tests/US-020-plano.md`. Cobertos em
`missao.controller.spec.ts` (`GET /missoes/:id`): detalhe com `pernas`
completo, `404` para id inexistente, `404` para missão de outro usuário,
`401` sem token.

Também incluído nesta sprint (DoD): `describe('Ciclo de vida completo...')`
em `missao.controller.spec.ts` — calcula uma Missão real via pipeline →
edita o Drone ou o Mapa usado → confirma que a Missão aparece desativada
(RN13) → confirma que a exclusão do Drone/Mapa continua bloqueada (RN15) —
exercitando RN13/RN15 com uma Missão nascida do pipeline real, não de
fixture, fechando o requisito da DoD da Sprint 06.

Suíte completa rodada com `pnpm test` ao final da sprint (US-017 a US-020):
19 suítes, 254 testes, todos passando. `pnpm typecheck` sem erros.
