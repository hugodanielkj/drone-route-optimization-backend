# US-002 — Login de usuário

## O que foi pedido

Permitir login com `nome` e `senha`, retornando um token de acesso; rejeitar
nome não cadastrado e senha incorreta com a **mesma** resposta genérica, para
evitar enumeração de usuários (RF-001.4).

## Passo a passo do que foi implementado

- `src/common/security/token.ts` — `gerarToken`/`verificarToken`, encapsulando
  `jsonwebtoken` (ver ADR-002). Payload contém só `{ sub: userId }`; `iat`/
  `exp` vêm da própria biblioteca.
- `src/modules/auth/auth.schema.ts` — schema Zod de login (`nome` e `senha`
  não vazios). Diferente do schema de cadastro (US-001), aqui `senha` não tem
  `min(8)` — a política de tamanho mínimo é uma regra de *cadastro*, não de
  *login*; validar tamanho no login não faz sentido (uma senha antiga mais
  curta, se algum dia a política mudar, continuaria precisando logar) e além
  disso reforçar o mínimo aqui vazaria informação sobre a política de senha
  para quem só está tentando autenticar.
- `src/modules/auth/auth.service.ts` — `login()`: busca usuário por `nome`;
  se não existe **ou** a senha não confere, lança `UnauthorizedError` com a
  mesma constante de mensagem (`CREDENCIAIS_INVALIDAS`) nos dois casos — não
  duas mensagens parecidas, o mesmo literal, para garantir na origem que não
  há diferença detectável.
- `src/modules/auth/auth.controller.ts` / `auth.routes.ts` — troquei o router
  placeholder criado durante US-001 (necessário para `app.ts` compilar antes
  de US-002 existir) pela rota real `POST /auth/login`.

## Alternativas de implementação consideradas

- **Timing-safe explícito (comparar contra um hash dummy quando o usuário não
  existe, para igualar o tempo de resposta entre os dois casos de erro)** —
  considerada e descartada nesta fase. bcrypt já tem custo computacional alto
  e relativamente constante por comparação; a diferença de tempo entre "não
  achou o usuário" (sem bcrypt.compare) e "achou mas senha errada" (com
  bcrypt.compare) é uma diferença de timing teórica, não coberta por nenhum
  critério de aceite das histórias do backlog. Registrado aqui como dívida
  consciente, não como ADR, por não ser uma decisão estrutural — é ajustável
  localmente em `auth.service.ts` se algum dia virar requisito.
- **Reutilizar o schema de cadastro para login** — descartada porque as
  regras de validação são semanticamente diferentes (ver acima), mesmo que
  a estrutura dos dois DTOs seja parecida.

## Como foi testado

Plano de testes: `docs/tests/US-002-plano.md` (11 casos). 10 dos 11 cobertos
diretamente nesta história:

- `src/modules/auth/auth.service.spec.ts` — casos 10 (mensagem idêntica nos
  dois cenários de erro, no nível de service) e 11 (token com `sub` e `exp`
  válidos, decodificado com `jsonwebtoken`).
- `src/modules/auth/auth.controller.spec.ts` — casos 1, 3, 4, 5, 6, 7, 8, 9,
  via Supertest contra `createApp()` e o banco de teste real.
- Caso 2 (token emitido é utilizável em rota protegida) é intencionalmente
  validado junto com US-003, que é quem introduz a primeira rota protegida —
  não faz sentido testá-lo isoladamente aqui.

Suíte rodada com `pnpm test -- auth`: 10 testes, todos passando.
