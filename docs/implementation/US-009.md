# US-009 — Cadastrar mapa

## O que foi pedido

Usuário autenticado cadastra um mapa com um ponto de carregamento e uma lista
de um ou mais pontos de irrigação, associado a si mesmo. Rejeita lista de
irrigação vazia (RN01) e coordenadas inválidas (falha de validação de DTO).

## Decisões de contrato tomadas com o usuário

- **Novas regras de negócio (RN16, RN17, RN18), adicionadas durante o
  planejamento desta sprint, não previstas no backlog original**: um Mapa não
  pode ter mais de 1000 pontos de irrigação (RN16); nenhum ponto de irrigação
  pode coincidir com o ponto de carregamento (RN17, erro dedicado); não pode
  haver dois pontos de irrigação com coordenadas iguais entre si (RN18, erro
  dedicado). Formalizadas em `regras-de-negocio.md`, propagadas para
  `RF-003.md` (RF-003.12 a RF-003.14) e para os critérios de aceite de
  `US-009.md`.
- **Formato de resposta agrupado (`pontoCarregamento: {x,y}`)**, em vez dos
  campos achatados que o Prisma usa internamente — registrado em `ADR-003`.
  Decisão tomada com o usuário via pergunta explícita antes de implementar,
  junto com a decisão de usar `.finite()` na validação de coordenada.

## Passo a passo do que foi implementado

- `src/modules/mapa/mapa.schema.ts` — `cadastroMapaSchema`:
  - `coordenadaSchema` valida `x`/`y` como `z.number().finite()` (bloqueia
    `NaN`/`Infinity`, que passariam em `z.number()` puro).
  - `pontosIrrigacao`: `z.array(coordenadaSchema).min(1)` (RN01) `.max(1000)`
    (RN16).
  - `.superRefine` cruza `pontoCarregamento` com `pontosIrrigacao`: emite um
    issue dedicado se algum ponto de irrigação coincidir com o ponto de
    carregamento (RN17), e outro issue dedicado se houver coordenadas
    duplicadas entre os próprios pontos de irrigação (RN18) — comparação por
    igualdade exata de uma chave `"x,y"` derivada de cada coordenada.
  - RN01, RN16, RN17 e RN18 são todas validadas na camada de schema (Zod), não
    no service: nenhuma delas depende de consulta ao banco, são invariantes
    estruturais do próprio payload — mesma categoria de RN01, que já era
    validada assim.
- `src/modules/mapa/mapa.service.ts` — `mapaService.cadastrar(usuarioId,
  input)`: um único `prisma.mapa.create` com nested write
  (`pontosIrrigacao: { create: input.pontosIrrigacao }`) e
  `include: { pontosIrrigacao: true }`. Atômico via transação implícita do
  Prisma no nested create, sem `$transaction` explícito.
- `src/modules/mapa/mapa.controller.ts` — `cadastrar`: parseia o body, chama o
  service com `req.usuarioId`, formata a resposta via `formatarMapa` (função
  local que agrupa `pontoCarregamentoX/Y` em `{x,y}` e mapeia cada ponto de
  irrigação para `{id,x,y}` — ver ADR-003) e responde `201`.
- `src/modules/mapa/mapa.routes.ts` — `POST /` registrado, com
  `autenticacaoMiddleware` aplicado a todo o router.
- `src/app.ts` — `app.use('/mapas', mapaRouter)` registrado, na mesma posição
  relativa de `droneRouter`.

## Alternativas de implementação consideradas

- **Validar RN16/RN17/RN18 no service, lançando `ValidationError` customizada**
  — descartada em favor de mantê-las no schema Zod: são checagens que só
  dependem do próprio payload (nenhuma consulta ao banco envolvida), a mesma
  categoria de RN01, que já vivia no schema. Manter as quatro juntas evita
  duas camadas diferentes de validação de payload para o mesmo tipo de regra.
- **Duas chamadas Prisma separadas (`mapa.create` + `pontoIrrigacao.createMany`)
  dentro de `$transaction`** — descartada: o nested write do Prisma já garante
  atomicidade em uma única chamada, sem o código extra de uma transação
  explícita.
- **Manter campos achatados na resposta, replicando `drone`** — descartada,
  ver `ADR-003`.

## Como foi testado

Plano de testes: `docs/tests/US-009-plano.md` (15 casos, incluindo os 3 novos
casos de RN16/RN17/RN18 e o caso de borda de proximidade sem igualdade exata).
Todos cobertos em:

- `src/modules/mapa/mapa.controller.spec.ts` (e2e): cadastro com um e múltiplos
  pontos de irrigação, coordenadas negativas/decimais, campos extras
  ignorados, associação ao usuário correto, exatamente 1000 pontos aceitos,
  ponto muito próximo do carregamento mas não igual aceito, lista vazia
  rejeitada, payload sem ponto de carregamento rejeitado, tipo inválido
  rejeitado, mais de 1000 pontos rejeitado (RN16), ponto de irrigação igual ao
  carregamento rejeitado (RN17), dois pontos de irrigação iguais rejeitados
  (RN18), ausência de token rejeitada.
- `src/modules/mapa/mapa.service.spec.ts` (unitário): criação com persistência
  de pontos de irrigação; testes diretos de `cadastroMapaSchema` para os casos
  de `NaN`/`Infinity` (não representáveis via transporte JSON, por isso
  testados no schema diretamente, não via Supertest) e para RN16/RN17/RN18.

Suíte rodada com `pnpm test`: 9 suítes, 135 testes, todos passando (nenhuma
regressão em Sprint 01 + Sprint 02). `pnpm typecheck` sem erros.
