# RF-001 — Autenticação e Cadastro de Usuário

## Contexto e objetivo

O sistema é multiusuário: cada usuário possui seus próprios Drones, Mapas e Missões,
e só pode acessar/operar sobre recursos que lhe pertencem. Esta funcionalidade cobre
o cadastro de usuários e o mecanismo de autenticação que protege todos os demais
endpoints do sistema (Drones, Mapas, Missões).

Conforme `.claude/rules/regras-de-negocio.md`, o objetivo desta fase é validar
conhecimento sobre o mecanismo de autenticação em si — não entregar uma experiência
de conta pronta para produção. Por isso, não há recuperação de senha nem
roles/permissões: apenas posse (ownership) simples.

**Ator envolvido:** Usuário (única persona do sistema nesta fase).

## Requisitos funcionais

- **RF-001.1** — O sistema deve permitir o cadastro de um novo usuário informando
  nome e senha. (RN09)
- **RF-001.2** — O nome do usuário deve ser único no sistema — é o identificador de
  login. Uma tentativa de cadastro com nome já existente deve ser rejeitada.
- **RF-001.3** — A senha deve ser persistida exclusivamente como hash, nunca em
  texto plano. (RN09)
- **RF-001.4** — O sistema deve permitir login com nome e senha, retornando um
  token de acesso a ser usado nas requisições subsequentes.
- **RF-001.5** — Toda operação sobre Drone, Mapa ou Missão deve exigir um token de
  acesso válido e deve operar exclusivamente sobre recursos pertencentes ao usuário
  autenticado. (RN11)
- **RF-001.6** — O sistema não deve oferecer nenhum mecanismo de recuperação de
  senha. A perda da senha implica perda permanente de acesso aos dados do usuário.
  (RN10)

## Requisitos não funcionais

- **RNF-001.1 (Segurança)** — A senha deve ser convertida em hash usando um
  algoritmo de hashing adequado para senhas (não um hash genérico de propósito
  geral). O algoritmo específico é uma decisão técnica a ser registrada como ADR na
  fase de implementação.
- **RNF-001.2 (Segurança)** — O mecanismo de emissão/validação do token de acesso
  (ex: JWT stateless, sessão) é uma decisão técnica a ser registrada como ADR na
  fase de implementação.
- **RNF-001.3 (Validação)** — Toda entrada de cadastro/login deve ser validada via
  DTO antes de chegar à lógica de negócio (conforme stack: class-validator).

## Restrições e premissas assumidas

- O nome do usuário é o único identificador de login — não há campo de e-mail nem
  outro identificador.
- Não há controle de papéis/permissões (roles): apenas ownership simples (RN11).
- Não há endpoint de "logout" com invalidação server-side do token nesta fase —
  presume-se token stateless cujo descarte é responsabilidade do cliente, salvo
  decisão em contrário registrada via ADR na implementação.
- Não há alteração de nome de usuário ou senha nesta fase (fora do escopo original
  do documento de regras de negócio, que não menciona essas operações).

## Perguntas em aberto

Nenhuma pendente — os pontos que estavam em aberto (algoritmo de hash, mecanismo de
token) foram classificados como decisões técnicas a resolver via ADR durante a
implementação, não como ambiguidade de regra de negócio.

## Pronto para virar histórias de usuário

RF-001.1 a RF-001.6 — sim, todos prontos.
